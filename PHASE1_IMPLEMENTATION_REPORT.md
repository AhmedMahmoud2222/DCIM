## 1. Executive Summary

Phase 1 is implemented and independently verified against real infrastructure, not
mocked or assumed. PostgreSQL 16 and Redis 7 were started for this session; a
PostgreSQL role, two databases, and the three required extensions (`uuid-ossp`,
`pgcrypto`, `btree_gist`) were created and confirmed installable. Two Alembic migrations
were written, autogenerated against the real schema, hand-reviewed, and applied from
scratch to both databases. 59 tests pass against those real instances. `ruff` and `mypy`
are clean on the backend; `tsc --noEmit`, `eslint`, and `vite build` are clean on the
frontend. A real `uvicorn` process and a real Celery worker were both started and
exercised via `curl` and a live outbox event to confirm the full authentication,
authorization, audit, and outbox pipelines work end-to-end over real HTTP and real
message delivery — not only through pytest's simulated transport.

Two genuine bugs were found and fixed during this verification, not glossed over: a
UUID server-default that was silently emitting a string literal instead of a SQL
function call (would have crashed the very first `INSERT`), and an outbox dispatcher
with no recovery path for an event stuck in `processing` after a lost delivery (a real
gap against §19's "failure recovery" requirement, closed with a stale-processing reclaim
window, itself covered by two new tests). Neither was discovered by static review —
both surfaced only because the corresponding code was actually run against a real
database and a real message broker.

Docker Compose was written and reviewed but **not executed** — no Docker daemon was
available in this session. This is the one meaningful gap in verification coverage and
is recorded plainly in `PHASE1_DEVIATIONS.md` (D1), not hidden inside a "done" claim.

## 4. Database Schema

18 tables across 2 migrations. `audit_log` is a genuinely partitioned PostgreSQL table
(`\dt` confirms `partitioned table`, not a plain table with a comment) with a default
catch-all plus 3 pre-created monthly partitions and a daily Celery task that keeps 3
months ahead of the current date. The application's `dcim_app` role holds `INSERT,
SELECT, TRUNCATE, REFERENCES, TRIGGER` on `audit_log` — confirmed via
`information_schema.role_table_grants`, and confirmed a second way by attempting a raw
`DELETE`/`UPDATE` as that role and getting `permission denied for table audit_log` back
from PostgreSQL itself, not from application code. A separate `dcim_retention_admin`
role exists (bootstrapped via `scripts/bootstrap_privileged_roles.sql`, run as
superuser, deliberately outside the Alembic chain — the migration role itself lacks
`CREATEROLE`, which is the least-privilege principle working as intended, not a gap).

`ManagedAsset.replaces_asset_id` carries a `UNIQUE` constraint (PostgreSQL correctly
allows unlimited `NULL`s while still enforcing uniqueness among non-null values, so this
needed no separate partial index) — verified with a real test that two different assets
each trying to claim replacement of the same old asset produces an `IntegrityError`.

## 5. API

20 endpoints, all under `/api/v1`, all discoverable via `/docs`. Every mutating route and
every sensitive-read route carries an explicit `require_permission(...)` dependency —
verified by grep as well as by test (`test_viewer_cannot_create_locations`,
`test_operator_can_transition_lifecycle_but_not_create`, etc.). Errors are RFC 7807
`application/problem+json`; every response carries `X-Request-Id`/`X-Correlation-Id`.

## 6. Authentication

Argon2id, 15-minute access tokens (memory-only on the frontend, never persisted),
7-day rotating refresh tokens delivered exclusively via an `HttpOnly`/`SameSite=Strict`
cookie (never in a JSON body, never reachable by frontend JavaScript), with a
double-submit CSRF token required on the two cookie-authenticated endpoints
(`/auth/refresh`, `/auth/logout`). Verified twice: once through pytest against the ASGI
transport, and once again through raw `curl` against a real running `uvicorn` process
with a real cookie jar — login → protected endpoint with the access token → refresh
rejected without CSRF header (403) → refresh succeeds with it (200, rotates token) →
reused old refresh token rejected (401).

---

## 7. Authorization

`User → RoleAssignment → Role → RolePermission → Permission`, five seeded roles, 11
permissions. H7's Option B is implemented literally: `RoleAssignment.scope_type`
defaults to `'global'` and the column exists, but **no query anywhere in this codebase
filters by site** — verified by code review of every `select()` call in
`app/api/v1/*.py`. Every protected route's permission requirement is exact-match, not
inferred from a broader one — this was the actual cause of the first three test
failures encountered during development (Engineer's seeded permissions were missing an
explicit `managed_asset:read` alongside `managed_asset:manage`) and was fixed by
correcting the seed data, not by adding hidden permission-inference logic.

---

## 8. Audit

Synchronous, in-transaction `AuditLog` writes on every location-hierarchy mutation,
every `ManagedAsset` create/lifecycle-transition, and every login. Distinct from and
never a substitute for the Outbox — verified structurally (separate tables, separate
service modules) and by test (`test_outbox_event_and_audit_row_commit_atomically_with_the_mutation`
checks both rows exist together; nothing in the codebase writes only one of the two for
the same mutation).

---

## 9. Outbox

`OutboxEvent` rows are written in the same transaction as their mutation (verified:
rolling back the transaction removes the event too — `test_outbox_event_does_not_survive_a_rolled_back_transaction`).
A real bug was found and fixed here: the dispatcher's original query only selected
`status='pending'` rows, so an event whose delivery was lost after being marked
`processing` (which is exactly what happened during manual smoke-testing, before the
Celery app's task-registration bug — see below — was fixed) would stall forever. Fixed
by reclaiming `processing` rows older than a 5-minute timeout, with two new tests
(`test_stale_processing_event_is_reclaimed_by_the_dispatcher`,
`test_recently_processing_event_is_not_reclaimed`) added specifically because this bug
was found, not written speculatively.

A second real bug was found and fixed in the same area: `celery_app.autodiscover_tasks()`
assumes a Django-style `<package>.tasks` submodule per app and silently found zero tasks
for this project's actual layout (multiple task modules directly under
`infrastructure/tasks/`) — the worker booted successfully and reported an **empty task
list**, which would have meant no outbox event was ever actually dispatched in
production despite every test passing (the tests call task functions directly, bypassing
Celery's task registry entirely, which is exactly how this was missed until a real
worker was started). Fixed with explicit imports; re-verified by inspecting
`celery_app.tasks` and by running a real worker end-to-end against a live event.

## 12. Observability

a fixed list: `password`, `access_token`, `refresh_token`, etc.). `request_id`/

## 13. Security

Focused adversarial review performed (§43 of the Phase 1 prompt), **not** external
penetration testing — stated explicitly, not implied otherwise:

| Area | Finding | Result |
|---|---|---|
| Login | Wrong password, unknown user | Both correctly return 401, no detail leakage beyond a generic message |
| Token type confusion | Refresh token presented as access token, and vice versa | Rejected (`jwt.InvalidTokenError`) — verified at both the unit and HTTP level |
| Tampered/malformed tokens | Bit-flipped JWT, non-JWT garbage string | Rejected, 401 |
| Privilege escalation | Viewer calling `POST /users` (Administrator-only), Viewer calling `POST /organizations` (manage-only) | Both correctly 403 |
| Object access | Unauthenticated calls to every protected resource | 401, consistently |
| Audit/idempotency interaction | Reused Idempotency-Key with a different body | Correctly rejected (422), not silently accepted |
| Concurrency | Two updates racing on the same `Room` with a stale `If-Match` | Second loses cleanly with 409, first's change is preserved |
| Input validation / injection | An organization name containing `'; DROP TABLE organization;--` | Stored and returned verbatim as data (parameterized queries via SQLAlchemy — confirmed the table still exists and is queryable afterward) |
| CORS | Preflight from the configured origin | Correct `Access-Control-Allow-Origin` header present |
| Error leakage | 404 response body | RFC 7807 shape only; no stack trace, no `sqlalchemy` string, checked with an actual substring search over the raw response text |
| Secret leakage | User-creation response body | No `password`/`hunter2` substring found in the raw response |
| Dependency vulnerabilities | `npm audit` | `react-router-dom` (moderate/high, production-shipped) upgraded to 7.18.4 and fixed; `esbuild`/Vite (moderate, dev-server-only) has no fix in the 5.x line, tracked as D4, not silently ignored |
| Database credentials / least privilege | `dcim_app` role's actual grants | No `UPDATE`/`DELETE` on `audit_log`; no `CREATEROLE` (confirmed by the role-creation step genuinely failing when attempted, which is exactly why the retention role is bootstrapped separately) |
| Container configuration | Dockerfile review | Non-root user (`dcim`) in the runtime stage, multi-stage build keeps build tools out of the final image, health checks defined | Not build-verified (D1) |

Automated/basic security validation completed. Not a claim of formal penetration testing.
