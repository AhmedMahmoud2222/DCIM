## VM design and owner decisions

First test: dedicated Ubuntu Server 24.04 LTS x86_64 VM (or approved supported 22.04 LTS); 4 vCPU, 8 GiB RAM, 100 GiB system/build disk, separate 100 GiB persistent PostgreSQL filesystem and separate 100 GiB encrypted backup target (off-VM copy preferred). Size up after observing images, build peak and workload. Avoid a Docker data-root on the database filesystem. Install supported Docker Engine, build plugin and Compose plugin **>=2.24.4**; record exact versions. Reserve at least 20 GiB and 20% free on system/build disk and 20% on database disk before deployment; alert at 80% utilization, page at 90%. Owner must approve VM region, cost, disk encryption/retention, DNS, SSH source CIDRs, backup target, and outbound allowlist.

First test access: no public app listener; firewall deny inbound by default and permit SSH only from named administrative VPN/bastion CIDRs. The four published sockets (5432, 6379, 8000, 8080) remain loopback. **Required for login:** owner-provisioned private DNS name `staging.<owner-domain>` and a trusted HTTPS reverse proxy reachable only over the approved VPN, terminating TLS on 443 and forwarding `/` and `/api/` to `http://127.0.0.1:8080` on the VM. The frontend nginx then proxies `/api/` to the backend. Browser origin and `CORS_ALLOWED_ORIGINS` must both be exactly `https://staging.<owner-domain>` (replace placeholder consistently). The backend retains `ENVIRONMENT: production` and therefore issues `Secure`, `SameSite=Strict` refresh/CSRF cookies; browser and API use one HTTPS origin. Do not use an HTTP SSH tunnel for login. Require a valid trusted certificate, private DNS and proxy before executing the smoke; the proxy is an **owner infrastructure configuration**, absent from the repository. Never expose database or Redis. Outbound: DNS, time, OS packages, GitHub API/git, container registries; block production/DCIM management networks and customer networks by routing/firewall, including Docker bridge egress. Check `172.20.0.0/16` does not overlap connected networks. No real collectors, device polling credentials or customer data.

Host identity `dcim-deploy` has SSH key authentication restricted to named operators, no password login; root-owned system packages and firewall. It owns `/opt/dcim` checkout and deployment state, `/var/backups/dcim` (0700) and `/var/log/dcim` (0700). PostgreSQL data `/var/lib/dcim-staging/postgres` is on dedicated mounted disk; on a verified empty first-use directory, assign the numeric `postgres` UID/GID discovered from the selected `postgres:16` image and verify 0700 mode and ownership. Never recursively change an existing database volume. Docker group membership is effectively root; permit it only to the trusted deploy identity or use audited privileged service execution, and do not treat it as a sandbox. Do not allow arbitrary Git writes or untrusted PR checkouts on this host. Docker daemon via systemd, enabled on boot; Compose `restart: unless-stopped` for persistent services, with a documented operator start after host reboot. One-shot migrations/bootstrap must not be blindly restarted on boot.

Stage-only secrets: independent high-entropy `POSTGRES_PASSWORD`, `DCIM_APP_PASSWORD`, `JWT_SECRET_KEY` and one 32-byte URL-safe base64 Fernet `CREDENTIAL_ENCRYPTION_KEY`. Use URL-safe alphanumeric password encoding because `DCIM_APP_PASSWORD` is inserted literally into the SQL bootstrap and URL; punctuation/quotes may corrupt init SQL or database URL. Generate offline on the VM through an approved secrets process, write private `.env` mode 0600 (directory 0700), store matching Fernet key in separate encrypted recovery storage, never echo values or include resolved `docker compose config` in evidence. Private read-only repository deploy key for Git fetch/clone; separate short-lived, read-only fine-grained GitHub token for verifier with Contents/Actions/Checks read. Token is passed to process environment for the duration and cleared afterward; repository access over Git SSH is independent of API token. Later PR: avoid raw secrets in container environment/`docker inspect`, provide external secret delivery and audited key rotation; existing one-key encryption cannot be rotated by simply replacing the variable.

Persistence: bind-mounted PostgreSQL is authoritative; Redis and beat `/tmp` are disposable under the current Compose. Review local catalog graphic/media persistence before any test that creates uploads: the stack has no media bind mount and data can be lost on rebuild. Plan daily PostgreSQL logical backups, pre-migration backup and verified isolated restore; include exact key/version metadata without secret value in evidence. Snapshot alone does not prove logical consistency. Capture filtered health, readiness, frontend response, Docker status and disk/log alerts; rotate retained evidence and never store `docker inspect` environment, raw `compose config`, full logs or `.env` in CI artifacts. Optional later: centralized alerting, registry-pinned immutable images, expanded offsite backup automation, secret manager, HA and production environment approval. **Private HTTPS ingress is required for first staging login**, while a repository-managed ingress template is optional.

## Prerequisites and acceptance checklist

- [ ] Owner approves region, VM/disks, SSH/VPN allowlist, egress segmentation, **private HTTPS DNS, trusted TLS certificate and restricted reverse proxy on 443**, backup destination and operator/on-call names.
- [ ] Ubuntu/Docker/Compose versions recorded; Compose >=2.24.4; data disk mounted and capacity thresholds met; empty first-use PostgreSQL directory verified owned by selected image's numeric postgres UID/GID with 0700 mode; localhost bindings confirmed in effective JSON without publishing secret fields.
- [ ] Staging-only synthetic dataset and separate credentials; private checkout/deploy key/API token; `.env` 0600, backups 0700; verified off-VM secret recovery copy.
- [ ] Full lowercase SHA on current main; newest CI and Deployment validation push/main workflow runs and required jobs successful for exact SHA; applicable Deployment Tools Test checked; validation-only dispatch successful.
- [ ] Eight services: postgres/redis/backend healthy; worker/beat/frontend running (frontend image also has HTTP health); migrate/bootstrap exited 0. API readiness and proxied endpoint return HTTP 200; browser at **`https://staging.<owner-domain>/`** authenticates and navigates inventory over the same HTTPS origin. Refresh/CSRF cookies are `Secure`, `SameSite=Strict`, scoped to `/api/v1/auth`; refresh succeeds with CSRF header, with no secret values in evidence.
- [ ] Migration revision and privileges checked; pre/post synthetic marker and backup/restore in isolated database verified. Rollback and failure intervention rehearsal pass; reviewer's sign-off recorded.
- [ ] No tokens/passwords/keys in logs, terminal captures or PR artifacts; evidence retained with restricted access. These gates establish **staging** only, never production readiness.
