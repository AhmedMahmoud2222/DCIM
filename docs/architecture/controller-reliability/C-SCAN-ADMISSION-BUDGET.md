| Term | Meaning |
| --- | --- |
| Unit | One ordered item discovered by a scan. It has a stable, opaque `unit_key` and a `unit_rev`, an opaque revision stamp supplied by the consumer that changes whenever the unit's observable state changes. `unit_key` values form a total order used only to compare keys with other keys. They are never compared with, or converted to, a time (SC-7). |
| Resolved unit | A unit whose evaluation is finished according to the consumer (Q4), with everything the consumer must keep durably recorded in the journal. |
| Open unit | A unit that is not resolved: incomplete, or its fetch failed retryably. |
| Scan state | The per-task record defined in SC-1. |
| Non-terminal task | A task in `ingested`, `pending`, `reserved` or `delivered_unconfirmed`. |
| Admission | Any mutation that adds a task record to the journal. |
| Run window | `RUN_WINDOW`, the platform's wall-clock limit for one execution (8 minutes in the reference environment). |
| Listing pass | One complete, ordered enumeration of the interval's unit listing (Q3) from its first page through a page flagged `exhausted`. |
| Listing epoch | An opaque token from the source (Q3a) that is equal across two reads only if no unit of the interval was added, removed or revised between them. |
| Coverage witness | The durable record in the scan state that a listing pass finished, bracketed by two equal listing-epoch reads, without observing any change (SC-7). |

## 2. Consumer-supplied inputs (named parameters)

| ID | Input | Contract |
| --- | --- | --- |
| Q1 | Inbound event functions | `event_authentic(event)`, a deterministic `task_id(event)`, a `deadline(event)` computed from event-intrinsic time, and an `interval(event)` `[interval_start, interval_end]` of wall-clock times with `interval_end <= deadline`. Policy and meaning belong to the consumer. |
| Q2 | `identity_valid(record)` | Re-verifies a stored task's identity tuple from the stored record alone. |
| Q3 | Unit listing | A paged listing of the units that belong to an interval by the consumer's own membership rule. It returns `(unit_key, unit_rev)` pairs in a stable `unit_key` order, with at most `PAGE_SIZE` per page, an opaque `page_token` that resumes the listing, the `listing_epoch` of Q3a, and an `exhausted` flag. `exhausted` is true only on a page after which the listing, as seen by that call, holds no further unit for the interval; an empty listing returns an empty page with `exhausted` true. If the source cannot state this reliably the consumer MUST NOT set the flag, and then `scan_complete` is never true (fail closed, SC-7). Q3 relates `unit_key` to the interval only through the consumer's membership rule; no order-preserving map from `unit_key` to time is required or assumed. |
| Q3a | Listing consistency capability | The consumer MUST declare exactly one `coverage_capability`. `epoch`: every page carries a `listing_epoch`, and `read_epoch(interval)` returns the current epoch; the epoch changes whenever any unit of the interval is added, removed or has its `unit_rev` changed, and does not change otherwise. `snapshot`: the first page request of a pass pins a snapshot, every `page_token` of that pass reads the same snapshot, the pinned snapshot identifier is returned as the page epoch, and `read_epoch(interval)` returns the live epoch of the source (equal to the pinned epoch only while the source is unchanged since the pin). `none`. This specification provides none of these primitives and invents no external atomic operation; `epoch` and `snapshot` are required consumer capabilities. With `none`, with an unreliable epoch, or when any epoch call fails, no witness is written and `scan_complete` is false (fail closed, SC-7). |
| Q4 | Unit evaluation | Returns `resolved`, `unresolved(reason)` or `unavailable` for a unit. Only the consumer may decide that a unit is resolved. This document never infers it. |
| Q5 | Retained items | Opaque per-task items the consumer needs to keep for resolved units, bounded by `RETAINED_BOUND`. |
| Q6 | Response facts | For every external read: status class and, when present, remaining quota, reset time and any retry-after hint, each recorded as a fact separate from the status class. |
| Q7 | Inbound source | Events remain re-listable for at least the longest task interval, and are never consumed destructively before T1 is confirmed (ING-1). |

## 3. Invariants

### 3.1 Journal size, admission and reserve (INV-B)
- **INV-B2** For every PUT this document supplies the `size_limit` of A:INV-B1 (contract A:P3), measured on the final signed bytes: `ADMISSION_LIMIT = JOURNAL_MAX_BYTES - JOURNAL_RESERVE_BYTES` for any mutation that adds a task record (including a T1 folded with T2 or any batch that includes an admission), and `MUTATION_LIMIT = JOURNAL_MAX_BYTES` for every other mutation.
- **INV-B3** `JOURNAL_RESERVE_BYTES` is reserved for mutations of already admitted tasks (state advancement, escalation, scan state, retained items). Admission MUST be refused (`JournalFull`, INV-F1) when its final signed bytes would exceed `ADMISSION_LIMIT`. Mutations of admitted tasks MAY consume the reserve, up to `MUTATION_LIMIT`.
- **INV-B3a** An existing-task mutation that returns `SizeLimitExceeded` at `MUTATION_LIMIT` is a reserve-sizing fault. The failing unit of work stops, an alert is raised, the task keeps its durable state, and no other task is blocked (INV-F4). It is never converted into a task rejection.
- **INV-B4** Every task record has a bounded maximum growth after admission (`TASK_GROWTH_BOUND`: bounded events, scan state, open units and retained items). Admission is also refused when the count of non-terminal tasks has reached `NONTERMINAL_CAP`. Configuration MUST satisfy `JOURNAL_RESERVE_BYTES >= NONTERMINAL_CAP * TASK_GROWTH_BOUND`; if it does not, the controller MUST refuse all admissions (fail closed) while still processing existing tasks. Hence every admitted task can reach a terminal state within the reserve.
- **INV-B5** No deletion or compaction of terminal tasks is specified or authorized (D-4). Terminal records do not grow (A:T9). When the journal fills with terminal records, admission fails closed with `JournalFull`.

### 3.2 Admission without starvation and task independence (INV-F, DL, ING)
- **INV-F1** An admission refused by INV-B2/B3/B4 returns the typed error `JournalFull`: no journal write, no external effect, no task record. It is auditable through a non-journal channel (workflow log and job summary).
- **INV-F2** `JournalFull`, `SizeLimitExceeded` for another task, and any ingestion failure MUST NOT block progress, reconciliation, deadline escalation or terminal transition of tasks already in the journal.
- **INV-F3** Admission MUST NOT consume execution budget reserved for reconciliation (BUD-1, BUD-3).
- **INV-F4** Tasks are independent. Any failure inside one task's unit of work (a retryable fetch error, a rate limit, a size fault, an invalid identity) is recorded for that task and the run continues with the next. Only the journal-level failures of A:P7 (`JournalInvalid`, `RollbackRefused`, `CheckpointUnavailable`) end the run, because no task may be acted on without a validated journal. Interaction between tasks happens only through CAS retries (A:INV-C3).
- **DL-1** (deadline sweep) Deadline escalation (T6, T7) is decided from the validated journal and the wall clock alone. It MUST be evaluated for every non-terminal task at the start of reconciliation, before and independently of any external read, and no retryable external failure, rate limit, retry-budget exhaustion or ingestion failure may skip, delay or replace it. Outages never extend a deadline (A:INV-D3). The deadline MUST be re-evaluated against the wall clock after every external call returns, before every retry, before every sleep or wait, and before every budget exit or exit-and-resume. A sleep or wait MUST NOT extend past the earliest stored deadline of a non-terminal task awaiting it; it is shortened to end at that deadline. When a deadline is found passed at any of these points, the T6/T7 write for that task is attempted in the same run, using the `R_reconcile` reserve (BUD-1), before the run retries, sleeps or exits. The reserve is sized for one T6/T7 write per non-terminal task of worst-case `W_write` each (BUD-1), and T6/T7 writes are issued before any SC-6 progress write once the usable tier has ended, so progress persistence can never consume time needed for escalation.
- **ING-1** Ingestion is idempotent: `task_id` is deterministic (Q1), a duplicate never writes, and an inbound event is not acknowledged or consumed before its T1 write is confirmed (A:INV-A5). After an ambiguous or lost T1 write the next run re-lists the event and decides from the durable journal alone (A:INV-A3).

### 3.3 Resumable scan state (SC)
- **SC-1** Each task carries a bounded scan state `{interval_start, interval_end, resolved_cursor, frontier, open_units, chunk_digests, retained, change_seq, pass, witness, reopen}`. The interval is fixed at admission and never changed. `resolved_cursor` is the greatest `unit_key` such that every unit at or before it is resolved. `frontier` is the greatest `unit_key` listed so far, and `frontier >= resolved_cursor` in `unit_key` order (key against key only). `change_seq` is a persisted counter (SC-7). `pass`, `witness` and `reopen` are defined in SC-7. Each `open_units` entry carries a durable `check_seq`, a per-task monotonic counter value assigned when the unit is last evaluated (0 when never revisited), written atomically in the same SC-6 write that records the revisit outcome; SC-5 orders revisits by lowest `check_seq` first, ties by `unit_key`, so the order survives restarts. Unqualified "the cursor" means `resolved_cursor`.
- **SC-2** Coverage: every unit with `resolved_cursor < unit_key <= frontier` is in exactly one of three states. (i) *Open*: in `open_units`, unresolved and individually tracked. (ii) *Pending*: inside the `reopen` range (SC-7) at or after `reopen.position`, unresolved and not yet re-evaluated; pending units are tracked only by the constant-size range and are not in `open_units`. (iii) *Confirmed resolved*: the consumer reported `resolved` (Q4), recorded only by absence from both `open_units` and the pending part of `reopen`. Absence from `open_units` therefore implies resolution only for units outside the pending part of `reopen`. A unit inside the `reopen` range before `reopen.position` has been re-evaluated and is resolved or in `open_units`. Pending units are unresolved for SC-3, so `resolved_cursor` never passes them; this relaxes neither no-skip (SC-3) nor `OPEN_UNITS_CAP` (SC-4).
- **SC-3** (never skip) `resolved_cursor` MUST NOT pass an open unit. A unit whose fetch failed retryably, or that is incomplete, becomes open and stays open until the consumer reports it resolved (Q4) or the task reaches a terminal state. Lack of progress is never read as absence of work.
- **SC-4** (frontier and open cap) `frontier` MAY advance beyond open units so that later pages are still discovered, but only while `open_units` is below `OPEN_UNITS_CAP`. At the cap `frontier` stops (fail closed; nothing is skipped). *Evaluate before advance.* Every unit listed by any page, whether in discovery, a pass (SC-7) or a `reopen` re-listing, is evaluated through Q4 in the same execution that lists it, and `frontier` (or `reopen.position`, or the pass `page_token`) MUST NOT pass a unit until its outcome is recorded in the write that advances the position (SC-6): `resolved` with its retained items (Q5), or `unresolved`/`unavailable` as an entry in `open_units`. A listed unit is never left unaccounted for, and absence from `open_units` (SC-2) therefore always means a Q4 `resolved`. If the cap or the budget is reached part-way through a page, the position stops at the last unit whose outcome was recorded, and the rest of the page is listed and evaluated again by a later execution. A unit first listed with `unit_key` beyond `frontier` is *initial discovery* and is evaluated here; it is not a change (SC-7).
- **SC-5** (revisit) Every execution re-evaluates open units, ordered by lowest durable `check_seq` first (SC-1) so a budget-limited run cannot starve any of them. A unit not revisited for lack of budget stays open. A changed `unit_rev` on an open unit triggers re-evaluation whether or not any attempt counter changed. When a unit resolves, `resolved_cursor` advances past it and past every following resolved unit in the same write.
- **SC-6** (retain before advance, ambiguous writes and conflicts) A write that advances `resolved_cursor`, `frontier`, `reopen.position` or the pass state MUST persist in the same write every retained item (Q5) for the units it passes, as one Document A write carrying a `mutation_id`. Retained items are keyed by `unit_key`, so persisting an item again for the same unit replaces it and never duplicates it. The outcome is decided as in Document A. The run that issued the write, while it is still alive and holds the `mutation_id` and the pre-write journal, classifies an ambiguous write by A:INV-A2. *Applied*, or a definite success: the positions and items are durable and the run adopts the confirmed journal (A:INV-A5); the write is not repeated. *Not applied* (A:INV-A2: the journal equals the pre-write journal), or a definite failure that changed nothing in the Store: the earlier positions are the durable positions and the units are scanned again. A definite 409/422 conflict (A:INV-C2) and a *superseded* classification are different: the attempted mutation did not apply, but the Store is not assumed unchanged, because another writer may have changed the journal and the scan positions. The run re-reads and validates the journal (A:INV-S2, A:INV-S4), re-derives the mutation on the current journal (A:INV-C3, A:INV-C4), and resumes from the positions in that fresh journal, which may be earlier or later than its own; it never assumes the earlier positions still hold. If the write is ambiguous and the recovery reads fail, the durable positions are *unknown* (A:INV-A3): the run stops advancing that task and acts on no assumption about either set of positions. The `mutation_id` and pre-write journal are process-local, so the next run does not classify (A:INV-A3). It reads and validates the journal and then decides from the durable scan state alone: it resumes scanning from whatever positions are durable, re-evaluating any span that was in fact already applied (idempotent because retained items are keyed by `unit_key`), and re-derives any needed mutation with a new `mutation_id`. It inherits no authorization from the earlier run. In every case no retained item is lost or duplicated and no unit is passed without its items.
- **SC-7** (change detection, coverage witness and completeness) A scan never decides completeness by comparing a `unit_key` with a time, and never infers that nothing changed from the absence of an observed change: an unobserved insertion leaves `change_seq` and every digest unchanged. Completeness rests on a durable witness bracketed by two reads of the source's listing epoch (Q3a).
  - *Change.* A change is any of: a unit not recorded in the scan state that is not initial discovery (a unit with `unit_key` at or before `frontier` that was never seen, whatever its key order and including one that sorts before `resolved_cursor`, or a unit listed beyond `frontier` by a page whose epoch differs from the epoch recorded by the pass), a changed `unit_rev` on a known unit, a chunk-digest mismatch (below), a unit becoming open, or a listing epoch that differs from the one recorded by the pass or the witness. Every change observed by any means, in any pass, revisit or check, MUST increment `change_seq` and clear `witness` in the same write that records it (SC-6), and any pass in progress is restarted from its first page.
  - *Chunk digests.* `chunk_digests` holds one digest over `(unit_key, unit_rev)` for each fixed-size chunk of resolved units in `unit_key` order; its length is bounded by `ceil(MAX_UNITS_PER_INTERVAL / CHUNK_SIZE)`, which is 0 for an empty interval and 1 when `CHUNK_SIZE` exceeds `MAX_UNITS_PER_INTERVAL`; the last chunk may be partial. A pass compares what it enumerates with the chunk digests. A mismatch (a changed `unit_rev` behind the cursor, or a unit inserted or removed behind it) is a change; it also moves `resolved_cursor` back to the start of the first mismatching chunk and records that chunk's range in `reopen = {range_start, range_end, position}`, a constant-size record, instead of loading its units into `open_units`. `CHUNK_SIZE` need not be at most `OPEN_UNITS_CAP`. Units in `reopen` are re-evaluated resumably: each execution, within budget and `MAX_PAGES_PER_RUN`, re-lists and re-evaluates from `position`, persisting `position` per SC-6. A unit that is not resolved on re-evaluation enters `open_units` only while `open_units` is below `OPEN_UNITS_CAP`; at the cap `position` stops at that unit, `frontier` stops (SC-4) and nothing is skipped or dropped. A later mismatch with range `[a, b]` updates the single range, in the same write that records the change, by this no-skip rule: `range_start` becomes the lesser of the old `range_start` and `a`; `range_end` becomes the greater of the old `range_end` and `b`; if the range was empty, or `a` is before the current `position`, `position` is set to `a` (the earliest newly affected key), otherwise `position` is unchanged; and `resolved_cursor` is moved to at most the new `range_start`. Units between two disjoint ranges are covered by the widened range and re-evaluated as well, which is idempotent (retained items are keyed by `unit_key`) but not minimal. A unit already re-evaluated before a rewind is re-checked and never assumed resolved, because pending status follows `position` (SC-2). `resolved_cursor` stays at or before `range_start` until `reopen` is empty. Units at or after `position` are *pending* (SC-2): unresolved for SC-2 and SC-3. A non-empty `reopen` prevents a witness and makes `scan_complete` false.
  - *Pass.* `pass = {change_seq_at_start, epoch_at_start, page_token, pages_done, running_digest}`. A pass MAY begin only when `coverage_capability` is not `none`, the wall clock is past `interval_end + SETTLE_SECONDS` (a time compared with a time; D-5), `open_units` is empty and `reopen` is empty. It begins by recording `epoch_at_start = read_epoch(interval)`. Each execution advances the pass within budget, bounded by `MAX_PAGES_PER_RUN`, persisting `page_token` and `running_digest` so that it is resumable. Every page's epoch MUST equal `epoch_at_start`; a different value is a change and restarts the pass. The pass enumerates the listing page by page through Q3 until a page with `exhausted` true.
  - *Witness.* The controller writes `witness = {change_seq, epoch, completed_at, unit_count, listing_digest = running_digest}` only when all hold: the pass has reached the `exhausted` page; `change_seq` equals `pass.change_seq_at_start`; `open_units` is empty; `reopen` is empty; `resolved_cursor` equals `frontier`; every unit listed by the pass has a recorded Q4 outcome (SC-4); and a *closing read* `read_epoch(interval)`, taken after the `exhausted` page was read, in the same execution and immediately before the witness write, equals `epoch_at_start`. The closing read is the only check that detects a unit added after the last page was read. A mismatch is a change: no witness, `change_seq` incremented, the pass restarts. If the closing read fails, or the pass ended in an earlier execution, no witness is written and the closing read is repeated. A pass that does not reach an `exhausted` page (flag never set, listing error, budget exit) leaves no witness. An insertion after the closing read but before the witness commits is not excluded by any primitive; it is caught by the live check in the Completeness bullet.
  - *Completeness.* `scan_complete(task)` is true only when all hold, evaluated on the validated journal: `witness` is present and `witness.change_seq == change_seq`; `witness.completed_at` is past `interval_end + SETTLE_SECONDS`; `open_units` is empty; `reopen` is empty; `resolved_cursor` equals `frontier`; a *live check*, made in the evaluating execution after the journal was read, returns `read_epoch(interval)` equal to `witness.epoch`; and a *post-check revalidation* follows it: the evaluating execution re-reads and validates the journal (A:INV-S2, A:INV-S4) after the live check returns and finds this task's `change_seq`, `witness`, `open_units`, `reopen`, `resolved_cursor` and `frontier` equal to those it evaluated. Any difference, or a failed re-read, makes `scan_complete` false for this execution (a concurrent run may have recorded a change, such as a unit becoming open, that does not alter the source epoch). A live-check mismatch is a change (increment `change_seq`, clear `witness`); if the write recording it cannot be confirmed, `scan_complete` is false for this execution. `scan_complete` is a point-in-time claim as of the live epoch read (the live check), and no later. The post-check revalidation guards only against journal changes by other runs; it reads the journal, not the source, so it cannot detect a unit the source gains between the live check and the re-read. That race is not excluded by any primitive. Consumers MUST NOT treat `scan_complete` as holding at the re-read or at any later time, and MUST NOT act on it as if no unit could have been added since the live check. A unit added after the live check is a later change, which the next live check or pass detects by epoch, handled by the consumer's own rules, which this document does not define. This document gives `scan_complete` no consequence.
  - *Fail closed.* With `coverage_capability` `none`, an unreliable or failing epoch, no `exhausted` flag from Q3, or `SETTLE_SECONDS` unset, no witness is written and `scan_complete` is false. A false value only delays the consumer and never skips work (ERR-2).
- **SC-8** (bounds) Per task: at most `OPEN_UNITS_CAP` open units, `RETAINED_BOUND` retained items, a bounded chunk list, and constant-size `change_seq`, `pass`, `witness` and cursor fields. On overflow the oldest diagnostic goes first; a cursor, an open unit, a `delivery_id`, the witness or a terminal record is never evicted. Scan pages are bounded by `PAGE_SIZE`, and a run stops scanning at `MAX_PAGES_PER_RUN` or when BUD-1 is reached, persisting progress per SC-6. More than one page of units (the reference case is over 100) is covered over several executions in the stable `unit_key` order without skipping or double evaluation.

**C-extension of A:T3** (A:P8: only narrows when T3 fires). T3 additionally requires: (i) `pre_post_budget_ok` is computed by BUD-6; (ii) the time left to the task's stored deadline is at least the BUD-6 sum; (iii) no applicable `not_before` (BUD-5) lies in the future. Otherwise the task stays `pending` and the deadline still governs. This document supplies `reserved_grace` as a parameter (D-5) and requires it to satisfy A:P2.

**POST fence** (narrows A:T3/A:T4 only, A:P8). The run that confirmed a T3 records a monotonic timestamp `t_issue` taken before it issued the T3 PUT. Immediately after the pre-POST re-read of A:INV-D1 and before the POST, it computes `elapsed = monotonic_now - t_issue` and issues the POST only if `elapsed + T_post_timeout <= reserved_grace`. Otherwise it issues no POST, writes nothing, and leaves the task `reserved` for T4r or T7. A run whose process was paused before the fence therefore fails the fence on resume. The POST is never issued on wall-clock reasoning alone. At-most-once (A:INV-D1) is unaffected: a POST after T7 still fails its T4 precondition and is never repeated.

This document defines no exception to A:T9. T6 and T7 satisfy A:P4. T6 is one resolution of `delivered_unconfirmed` under A:P5, issues no POST, and leaves every other resolution to the consumer.

## 5. Execution budget (BUD)

`RUN_WINDOW` is the platform limit. `R_reconcile` (time reserved for read, validation, deadline sweep and escalation writes) and `R_exit` (final write and logging margin) are parameters (D-5).
- **BUD-1** Time since the run started is divided into three tiers. *Usable*: until `RUN_WINDOW - R_reconcile - R_exit`, all work is allowed (ingestion, discovery, open-unit revisits, listing passes, task work, T3). *Reconcile reserve*: from there until `RUN_WINDOW - R_exit`, only the DL-1 sweep, T6/T7 writes with their checkpoint advances, and the SC-6 persistence of progress already made are allowed; no new page, revisit, ingestion call, T3 or POST is started. *Exit*: the last `R_exit` is for the final write and logging only. Every external call has a timeout no greater than the time left in the tier of the work that issues it, so no call can run into a later tier. Let `W_write = (1 + MAX_CAS_RETRIES) * (T_reread + T_write) + T_checkpoint + MAX_PUT_RECOVERY_READS * T_read`, the worst case of one Document A write including its CAS retries, checkpoint advance and ambiguous-write recovery reads (A:P6). Each non-terminal task is allowed at most one T6/T7 write and at most one coalesced SC-6 progress write (all progress made by that task in this run in a single write) in the reserve tier. `R_reconcile` MUST be at least `T_sweep + N_nonterminal * 2 * W_write`, where `T_sweep` is the worst-case DL-1 sweep and `N_nonterminal` is bounded by `NONTERMINAL_CAP`; the configuration is refused (fail closed, no new work other than DL-1) if it is not. In the reserve tier all T6/T7 writes are issued before any SC-6 progress write, and an SC-6 write that cannot complete inside the reserve is not started: its progress is abandoned, the durable positions stay the earlier ones (SC-6, ERR-2), and the units are scanned again.
- **BUD-2** Budget is checked before each task, page, retry and call. "Exhausted" means the usable tier of BUD-1 has ended, not the run window. When it is exhausted the run stops admitting, scanning and starting task work, persists progress (SC-6) inside the reconcile reserve under the worst-case bound `T_sweep + N_nonterminal * 2 * W_write` of BUD-1 (T6/T7 writes first, then at most one coalesced SC-6 write per task, none started if it cannot finish), and ends with status `budget_exhausted_resume`. It MUST NOT fail the run only because work remains.
- **BUD-3** Reconciliation of existing tasks comes before ingestion. Order: DL-1 sweep first, then tasks by nearest deadline, then open-unit revisits (SC-5), then listing passes (SC-7), then ingestion.
- **BUD-4** Retry sleeps count against the budget. A sleep that would cross the usable budget is not taken: the task whose call requested it is deferred for the rest of this run (its unit stays open, no `not_before`, no rejection, DL-1 still applies) and the run continues with every other eligible task; the run exits-and-resumes only when the usable budget has ended (BUD-2) or no eligible work remains (ERR-5, INV-F4). Ingestion retries are bounded per call by `MAX_INGEST_RETRIES` and in total by BUD-1; when they are exhausted ingestion ends for this run as `ingestion_deferred`, reconciliation is unaffected (INV-F2), and the run still completes with that status shown in the job summary.
- **BUD-5** Quota-exhaustion delays follow section 6. A quota-exhausted response persists a `not_before` for its scope and defers that scope only. With a task-scoped `not_before` (D-7) the affected task's `not_before` is persisted and the run continues with every other task whose scope has no future `not_before`; with a global scope all scopes are deferred. The stated wait is taken inside the run only if it fits the usable budget and no other eligible work remains. The run ends for quota reasons only when no eligible work remains or the budget is exhausted (BUD-2). A deferred task is neither failed nor rejected, and DL-1 still applies to it. A persisted `not_before` is honored: a task whose `not_before` lies in the future is not eligible for external reads or T3 in this run. A `not_before` is a constant-size journal field per scope; the scope set (per task or global) is D-7. Only the quota-exhausted class of section 6 may persist a `not_before`.
- **BUD-6** `pre_post_budget_ok` is true only when remaining usable time is at least `T3_phase + T_reread + T_post_timeout + T4_phase`, using the timeouts in force (A:P2, A:INV-D1), where `T3_phase = (1 + MAX_CAS_RETRIES) * (T_reread + T_write) + T_checkpoint + MAX_PUT_RECOVERY_READS * T_read` and `T4_phase = (1 + MAX_CAS_RETRIES) * (T_reread + T_write) + T_checkpoint + MAX_PUT_RECOVERY_READS * T_read`. Both the authorizing T3 write and the outcome T4 write therefore carry their own checkpoint advance (A:INV-S5, A:INV-S6) and their own worst-case ambiguous-write recovery and conflict retries. Because T3 conflicts may consume part of `T3_phase`, the run MUST also recompute, after the T3 is confirmed and immediately before the POST (together with the POST fence), that the remaining usable time is at least `T_reread + T_post_timeout + T4_phase`; if not, it issues no POST, writes nothing, and leaves the task `reserved` for T4r or T7. The sum must fit before the end of the usable tier of BUD-1, so a T4 can still be committed and checkpointed after the POST without entering the exit tier.
- **BUD-7** The CAS retry limit `MAX_CAS_RETRIES`, the recovery-read limit `MAX_PUT_RECOVERY_READS` and the per-call fetch retry limit are explicit parameters (D-5). They satisfy A:P6.

## 6. Error taxonomy (reads, lookups and fetches)

Store PUT outcomes and POST outcomes are classified by Document A (ambiguous writes, conflicts, T4n) and are not restated here. Classification below uses only Q6 facts and never infers a quota state that the response does not show. Precedence: a 429, or a response whose quota facts explicitly show remaining quota 0, is quota exhausted; every other 5xx or timeout is transient, whatever hints it carries.

| Class | Examples | Treatment | Permanent? |
| --- | --- | --- | --- |
| Quota exhausted | 429; any response (including a 403 or 5xx) whose quota facts explicitly show remaining quota 0. A retry-after or reset hint on such a response states the wait | Persist `not_before` for the scope and defer that scope; wait inline until the stated time only if it fits the budget and no other eligible work remains; the run continues with other eligible scopes and ends only per BUD-5. Backoff counter resets only after a success, never on quota refresh | No |
| Transient | 5xx, timeout, connection error, truncated body, whose quota facts show remaining quota above 0 or are absent. This holds even when the response carries a retry-after hint or a distant reset time | Bounded jittered exponential backoff inside the budget. When the per-call retry limit of that task's call is exhausted, the failure is recorded for that task only (its unit stays open, SC-3; ERR-2), the task is not retried again in this run, and the run continues with every other eligible task (INV-F4, ERR-5). Exit-and-resume of the whole run happens only when the usable budget is exhausted (BUD-2) or no eligible work remains. A retry-after hint on such a response is a transient backoff hint only: it may raise the next sleep to at most `MAX_TRANSIENT_HINT`, and only if that fits the budget; it is never persisted as `not_before`. **Never waits for a quota reset** | No |
| Auth or forbidden | 401; 403 without quota signal | The dependent step stops, no state change, alert. The DL-1 sweep is unaffected | No |
| Unavailable | 404 or 410 on a unit or artifact | Reported to the consumer as `unavailable` (Q4). The unit stays open unless the consumer resolves it by its own rule; it is never skipped by the scan | Not by this document |
| Invalid request | 422 on a read | The step stops with an alert; no task is rejected because of it | No |
| Admission | `JournalFull`, `EventExpired` | INV-F1 | n/a |
| Budget | Execution time budget exhausted (BUD-2), or no eligible work remains | Persist progress, exit-and-resume. A per-task retry limit is not this class; it is handled under Transient and ends only that task's work for this run (ERR-5) | No |
| Journal-level | A:P7 errors | Run ends per INV-F4 and A:T10 | n/a |

- **ERR-1** A retryable failure (any class above except where the consumer resolves the unit) MUST NOT produce a permanent outcome and MUST NOT advance `resolved_cursor` past the unit (SC-3). A permanent outcome for a unit requires a successful fetch and the consumer's decision.
- **ERR-2** Exhausting a retry or time budget is never converted into a rejection. The unit and task remain pending until the task deadline, after which T6 or T7 applies.
- **ERR-3** Failures of the journal Store itself while handling a unit follow Document A (INV-A3, INV-A5) and never reject a unit or a task.
- **ERR-5** Exhausting the retry limit for one task's calls is scoped to that task for the rest of the run. It never ends the run while usable budget and other eligible tasks remain (INV-F4, BUD-2).
- **ERR-4** A 5xx or timeout whose quota facts show remaining quota above 0, or no quota facts, is never treated as quota exhaustion, and no retry-after hint or reset time on it changes that class (section 6 precedence).

## 7. Fault-injection harness (applies to every FC test)

- **Seeded fake Store and anchor** as in Document A section 5, extended with size accounting of the final signed bytes and a settable `JOURNAL_MAX_BYTES`.
- **Fake clock** (wall and monotonic) with a settable run window; the harness uses `RUN_WINDOW` = 480 s as a fact of the reference platform and symbolic values for every other parameter. Harness values are test settings, not policy.
- **Fake external API:** paged unit listing with `unit_rev`, an `exhausted` flag, a `listing_epoch` per page and a callable `read_epoch` that changes on any add, remove or revision (a mode with capability `none` returns no epoch), hooks that mutate the source between any two calls, injectable status codes, and quota facts and retry-after hints as independent fields, counters per call kind, and a record of every wait requested. Unit keys are generated from the seed and may be deliberately non-time-sortable (random identifiers whose order bears no relation to creation time).
- **Fake inbound source** with re-listable events; **kill points** between any two journal writes.
- Assertions use only observable fake state. Tests are specified here; none has been run.

## 9. Unresolved owner decisions and risks

- **D-3** Values of `JOURNAL_MAX_BYTES`, `JOURNAL_RESERVE_BYTES`, `NONTERMINAL_CAP`, `TASK_GROWTH_BOUND` and `MAX_ADMISSIONS_PER_RUN`. G-10 remains open until they are set. No value is invented here.
- **D-4** Archival or retention for terminal tasks (INV-B5). No deletion is authorized.
- **D-5** Budget and scan parameters: `R_reconcile`, `R_exit`, `reserved_grace`, `PAUSE_MARGIN` (T7), retry limits (BUD-7), `T_read`, `T_write`, `T_checkpoint`, `T_reread`, `T_post_timeout` (BUD-6), `MAX_TRANSIENT_HINT` (section 6), `PAGE_SIZE`, `MAX_PAGES_PER_RUN`, `OPEN_UNITS_CAP`, `RETAINED_BOUND`, `CHUNK_SIZE`, `MAX_UNITS_PER_INTERVAL`, `SETTLE_SECONDS` (SC-7), and the task deadline duration behind Q1.
- **D-7** Scope of `not_before`: per task or global (BUD-5). Both conform to this document.
- **U-1** Wall-clock source and skew for stored deadlines (DL-1) and for `SETTLE_SECONDS` (SC-7). A skewed runner clock could escalate or complete early or late. No mitigation is specified.
- **U-2** Whether an escalation notice may be a POST. If so, it needs its own reservation under Document A:T3 and is out of scope here.
- **U-3** Whether persistent `ingestion_deferred` or `budget_exhausted_resume` should eventually fail the run for visibility.
- **U-4** Whether an artifact or unit that is permanently `unavailable` may ever be closed. This document keeps it open until the task deadline; closing it is a consumer decision (Q4).
- **U-5** Inbound events that are consume-once at the source would violate Q7 and risk loss at an ambiguous T1.
- **U-6** Whether a source can provide the Q3a `epoch` or `snapshot` capability and set the `exhausted` flag reliably, and bound how late a unit may appear after `interval_end`. If it cannot (`none`), `scan_complete` stays false and the consumer relies on the task deadline. This is a consumer property, not defined here. Even with the capability, `scan_complete` is only a point-in-time claim (SC-7).
- **U-7** Whether a T3-confirming run descheduled after the POST fence and before the POST, for longer than `reserved_grace + PAUSE_MARGIN`, is acceptable. No durable lease, revocation or atomic claim is available in the Store or the external API, and this document invents none. Residual outcome: one POST after T7 escalation, never a second POST (A:INV-D1). Closing this needs an owner decision on a lease primitive or on accepting the risk.
- Risk: the pass, the epoch reads and the digest comparison (SC-7) cost listing calls on every execution until a witness exists; their bounds are parameters (D-5). The seam with the consumer is Q3/Q3a/Q4 and `scan_complete`.
- G-6 (journal storage failures) is Document A's; ERR-3 only states that C adds no rejection for them. This document selects no credential, secret, token, ref protection or permission.
