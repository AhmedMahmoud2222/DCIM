# DCIM MVP v0.1 Design

## Goal

Deliver one demonstrable, outbound-only operational path: a site-side collector polls a controlled SNMP device, durably queues normalized observations, forwards acknowledged batches to Central DCIM, stores deduplicated telemetry, evaluates basic alarms, and exposes current state and history in the existing React product.

## Boundaries

Central remains the sole authority for inventory, integration configuration, telemetry, alarms, audit and outbox. `edge_collector/` is an isolated Python package: it may use HTTP, SQLite, stdlib and protocol libraries, but must not import central `app` ORM/session/RBAC modules. It holds only local configuration and unacknowledged observations.

Existing ManagedAsset, locations, placement, power, Integration, Collector, HMAC authentication, idempotency, audit and outbox remain the source of truth and are extended rather than replaced. The existing centralized REST network policy is reused; collector-target policy uses the same explicit allow-list principles. Global human RBAC remains intentional and no site-scoped human RBAC is introduced.

## Data flow

```text
Configured Integration + thin MetricMapping
  -> Edge SNMP v2c / REST / ICMP poll
  -> normalize canonical metric
  -> SQLite queue transaction
  -> signed bounded HTTP batch
  -> central per-record acknowledgement
  -> PostgreSQL TelemetryReading (occurred_at + received_at + dedup key)
  -> transactional outbox event
  -> alarm evaluator
  -> dashboard/latest/history APIs
```

The queue deletes a row only for `accepted` or an idempotent `duplicate` ACK. Transient transport failure, 429/5xx, malformed response and unacknowledged records remain durable and receive bounded exponential backoff with jitter. Queue limits are records, bytes and retention duration; the explicit full policy drops the oldest record only after recording an observable local drop counter/event, preserving fresher operational readings.

## Central MVP model

One Alembic revision creates thin `integration_metric_mapping`, `telemetry_reading`, `alarm_rule`, and `alarm` tables. Mapping belongs to an Integration and carries source identifier/OID, canonical metric, unit, scale and label. This is deliberately compatible with future VendorProfile/DeviceProfile ownership without claiming to implement those catalog layers.

Telemetry has integration ID, optional ManagedAsset ID, canonical metric, numeric/text value, unit, occurred_at, received_at, collector dedup key and JSON labels/quality. A unique logical identity plus idempotent ingest prevents replay duplicates. Composite indexes support integration/asset + metric + time, latest readings, and bounded history.

Alarm rules support high threshold, low threshold and availability-unavailable. A rule has at most one currently open alarm. Alarms transition `ACTIVE -> ACKNOWLEDGED -> CLEARED`; reopening after clear creates a new lifecycle. Every transition is audited and produces an outbox event. Telemetry ingestion calls an application-level evaluator, not alarm ORM methods.

## APIs and UI

Central exposes bounded latest, integration/asset readings, history with fixed/default range caps and downsampling, alarm list/acknowledge, dashboard summary and equipment operational summary. The dashboard combines existing capacity summaries with collector health, active alarms and latest canonical values using bulk queries. The equipment view composes identity/location/power with telemetry/alarm/history and source integration.

Navigation separates Infrastructure, Operations, Connectivity and Power, with Dashboard as the landing page. Demo data is explicitly opt-in/labelled and includes one site, room, racks, equipment, power topology, collector/integrations, readings and alarm states.

## Reliability and security

SQLite uses a versioned migration table, WAL, transactions, integrity checks and corrupt-queue fail-closed diagnostics. Credentials come from environment/local permission-restricted config and are never logged. Central and edge target validation use explicit network, port, scheme and method policy. SNMP v2c community strings are write-only/log-redacted. Central collector authentication, assignment checks and bounded request parsing remain mandatory.

## Validation

Implement test-first. Unit tests cover queue persistence, retry, capacity, partial ACK and corruption; wire-level tests use a controlled local SNMP agent rather than mocked transport. Central PostgreSQL tests cover migration, deduplication, delayed/out-of-order readings, alarm lifecycle/concurrency, API bounds and dashboard query count. The acceptance demo records the exact SNMP -> queue -> central -> telemetry -> alarm flow and a simulated WAN outage/replay.

## Deferred scope

No full vendor/device catalog, SNMPv3 unless safely added after v2c, Timescale/Kafka/ClickHouse, advanced correlation, ML/AI, 3D, full site-scoped human RBAC, multi-region or production claim. Existing nonce/heartbeat retention, secret rotation, reconciliation outbox and polling query scaling remain deferred unless this vertical slice requires a narrow correctness change.
